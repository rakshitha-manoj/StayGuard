# Dataset versioning with DVC: v1-raw vs v2-clean

Two dataset versions are tracked with DVC (remote `gs://stayg-510316-stayguard-dvc/dvcstore`) and tagged in git:

| Git tag | What it holds | Where the data pointer lives |
|---|---|---|
| `v1-raw` | Raw Kaggle `hotel_bookings.csv`, 119,390 rows | `data/raw/hotel_bookings.csv.dvc` |
| `v2-clean` | Output of the `dvc.yaml` pipeline (validate, preprocess, validate) | `dvc.lock` (`preprocess` stage out) |

Notes:
- Exact duplicates **are** removed in v2 (last preprocessing step, on the final encoded frame, `keep="first"`), so identical rows cannot land in both the train and test split and inflate test metrics. The count (33,493) is higher than the 31,994 raw duplicates because dropping the leaky columns and the agent/company IDs makes previously distinct rows identical. Caveat: some of these are legitimate repeated group bookings; we trade a little data for honest test metrics. `validate_clean` fails on any duplicate row.
- The cancel rate drops from 0.3704 to 0.2766 because of the dedupe: the removed duplicate rows had a 61.2% cancel rate (checked by running the pipeline up to that step, where the rate was 0.3708). `lead_time mean` and `adr mean` shift for the same reason.
- `assigned_room_type` was dropped as **target leakage**: it is assigned at check-in. Where it differs from `reserved_room_type` (14,917 rows) the cancel rate is 5.4%, versus 41.6% when the two are equal. `validate_clean` fails if the raw column or any `assigned_room_type_*` column is present.
- v2 has 70 columns because the 8 remaining categorical columns are one-hot encoded; the file is smaller on disk than v1 because far fewer rows remain.
- The processed CSV is written with LF line endings (`lineterminator="\n"`), and the `reports_data/*.json` files with LF too, so every md5 is identical on Windows and Linux.

## Preprocessing steps and rows affected

Counts are logged by `src/preprocess.py` to `reports_data/preprocess_log.json`.

| # | Step | Effect |
|---|---|---|
| 1 | Drop leaky columns `reservation_status`, `reservation_status_date`, `assigned_room_type` | 3 columns removed (known only after the outcome, or set at check-in) |
| 2 | Impute `children` null to 0 | 4 values |
| 3 | Impute `country` null to "Unknown" | 488 values |
| 4 | `agent` / `company` to `has_agent` / `has_company`, drop raw IDs | 2 columns replaced (IDs are high-cardinality nominal codes, so no ordinal meaning and a very wide one-hot) |
| 5 | Add `total_nights`, `total_guests` | 2 columns added |
| 6 | Remove zero-guest rows (`total_guests == 0`) | 180 rows removed |
| 7 | Remove negative `adr` rows | 1 row removed |
| 8 | Cap `adr` at the 0.995 quantile (275.0) | 588 values capped, 0 rows removed (cap computed on the full dataset before the train/test split: a documented, mild simplification) |
| 9 | `arrival_date_month` to 1-12 | all rows |
| 10 | Keep top 10 countries (PRT, GBR, FRA, ESP, DEU, ITA, IRL, BEL, BRA, NLD), rest to "Other" | all rows |
| 11 | One-hot encode 8 categoricals (sorted columns, 0/1 ints), target last | 70 columns |
| 12 | Drop exact duplicate rows on the encoded frame (`keep="first"`) | 33,493 rows removed |

Rows: 119,390 in, 181 removed by the validity filters (180 + 1), 33,493 removed as duplicates, **85,716 out**. Final shape 85,716 x 70, all numeric, `is_canceled` last, no scaling (done in the Phase 3 model pipeline).

Validation (`reports_data/validation_*.json`): raw passes the hard checks with soft issues (nulls in 4 columns, 1 negative adr, 588 adr above cap, 180 zero-guest rows, 31,994 duplicate rows, 3 leaky columns present); clean passes all strict checks, including zero duplicate rows and no leaky or `assigned_room_type_*` columns.

## Benefits of data versioning

- **Reproducibility.** A git commit pins the code, `params.yaml` and the exact data hashes (`.dvc` / `dvc.lock`). Checking out a commit and running `dvc pull && dvc repro` rebuilds the identical dataset (at the two tags, pull the raw file by target: `dvc pull data/raw/hotel_bookings.csv.dvc`, see Rollback).
- **Rollback.** Go back to the raw-only version, then return:
  ```
  git checkout v1-raw
  dvc checkout data/raw/hotel_bookings.csv.dvc
  git checkout main && dvc checkout
  ```
  Name the `.dvc` target explicitly when checking out either tag. Both tags predate a `.gitignore` fix: their `data/raw/*` pattern makes DVC skip the `data/raw/` folder, so a bare `dvc checkout` there deletes the raw CSV instead of restoring it. On `main` a bare `dvc checkout` / `dvc pull` works. On Windows with `core.autocrlf=true`, visiting a tag leaves CRLF copies of `src/*.py` behind (the tags predate `.gitattributes`). If `dvc status` on `main` then reports modified deps, run `git rm -r -q --cached . && git reset -q --hard`.
- **Auditability.** Every change to the data is a git commit with a message, author and tag; `dvc diff v1-raw v2-clean` shows what changed, and the logged per-step row counts show why.
- **Collaboration.** The data lives in a shared GCS remote while git holds only small pointer files. A teammate clones the repo and runs `dvc pull`, with no CSV emailing.
- **Linking data to model runs.** In Phase 3 each MLflow run will log the data version tag and DVC md5 as params, so any model can be traced to the exact data it was trained on.

## How to reproduce

```powershell
.venv\Scripts\Activate.ps1      # stages call plain `python`
dvc pull                        # fetch raw CSV (and cached outputs) from GCS
dvc repro                       # validate_raw -> preprocess -> validate_clean
python -m src.data_report       # regenerate the comparison table
```
