# Dataset versioning with DVC: v1-raw vs v2-clean

Two dataset versions are tracked with DVC (remote `gs://stayg-510316-stayguard-dvc/dvcstore`) and tagged in git:

| Git tag | What it holds | Where the data pointer lives |
|---|---|---|
| `v1-raw` | Raw Kaggle `hotel_bookings.csv`, 119,390 rows | `data/raw/hotel_bookings.csv.dvc` |
| `v2-clean` | Output of the `dvc.yaml` pipeline (validate, preprocess, validate) | `dvc.lock` (`preprocess` stage out) |

## Preprocessing steps and rows affected

Counts are logged by `src/preprocess.py` to `reports_data/preprocess_log.json`.

| # | Step | Effect |
|---|---|---|
| 1 | Drop leaky columns `reservation_status`, `reservation_status_date` | 2 columns removed (known only after the outcome) |
| 2 | Impute `children` null to 0 | 4 values |
| 3 | Impute `country` null to "Unknown" | 488 values |
| 4 | `agent` / `company` to `has_agent` / `has_company`, drop raw IDs | 2 columns replaced (IDs are high-cardinality nominal codes, so no ordinal meaning and a very wide one-hot) |
| 5 | Add `total_nights`, `total_guests` | 2 columns added |
| 6 | Remove zero-guest rows (`total_guests == 0`) | 180 rows removed |
| 7 | Remove negative `adr` rows | 1 row removed |
| 8 | Cap `adr` at the 0.995 quantile (275.0) | 588 values capped, 0 rows removed (cap computed on the full dataset before the train/test split: a documented, mild simplification) |
| 9 | `arrival_date_month` to 1-12 | all rows |
| 10 | Keep top 10 countries (PRT, GBR, FRA, ESP, DEU, ITA, IRL, BEL, BRA, NLD), rest to "Other" | all rows |
| 11 | One-hot encode 9 categoricals (sorted columns, 0/1 ints), target last | 81 columns |

Rows: 119,390 in, 181 removed (180 + 1), **119,209 out**. Final shape 119,209 x 81, all numeric, `is_canceled` last, no scaling (done in the Phase 3 model pipeline).

Validation (`reports_data/validation_*.json`): raw passes the hard checks with soft issues (nulls in 4 columns, 1 negative adr, 588 adr above cap, 180 zero-guest rows, 31,994 duplicate rows, 2 leaky columns present); clean passes all strict checks.

## Benefits of data versioning

- **Reproducibility.** A git commit pins the code, `params.yaml` and the exact data hashes (`.dvc` / `dvc.lock`). Checking out a tag and running `dvc pull && dvc repro` rebuilds the identical dataset.
- **Rollback.** Go back to the raw data in two commands, then return:
  ```
  git checkout v1-raw && dvc checkout
  git checkout main && dvc checkout
  ```
- **Auditability.** Every change to the data is a git commit with a message, author and tag; `dvc diff v1-raw v2-clean` shows what changed, and the logged per-step row counts show why.
- **Collaboration.** The data lives in a shared GCS remote while git holds only small pointer files. A teammate clones the repo and runs `dvc pull`, with no CSV emailing.
- **Linking data to model runs.** In Phase 3 each MLflow run will log the data version tag and DVC md5 as params, so any model can be traced to the exact data it was trained on.

## How to reproduce

```powershell
.venv\Scripts\Activate.ps1      # stages call plain `python`
dvc pull                        # fetch raw CSV (and cached outputs) from GCS
dvc repro                       # validate_raw -> preprocess -> validate_clean
python -m src.data_report       # regenerate the comparison table
```
